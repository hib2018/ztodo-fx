# ztodo-fx Constitution

## Core Principles

### I. UI非依存のコマンドコア

タスク管理、GitHub Issue連携、Proposalの生成・検証・承認、永続化に関する
業務ルールは、UIに依存しないコアへ集約しなければならない。CLIと将来のTUIは
同じコアAPIを呼び出す薄いアダプターとし、業務ルールを重複実装してはならない。
これにより、UIの追加や変更がタスク管理の意味やデータ形式を変えない状態を保つ。

### II. 人間が統制するProposal

エージェントは、選択されたIssueと対象ワークスペース内のコード、設定、ドキュメント、
Git履歴を読み取り、実装可能なProposalを生成できる。ただし、Proposal生成中の調査は
読み取り専用でなければならず、ファイル変更、ビルド、テスト、外部サービスの更新を
実行してはならない。Proposalは常に候補として扱い、利用者はTaskへの反映前に編集、
追加、削除、並べ替え、却下できなければならない。明示的な承認なしにProposalをTaskへ
反映してはならない。

### III. データ完全性

永続化する入力は全体を検証し、検証成功後にのみAtomic保存しなければならない。
検証失敗、処理中断、書き込み失敗では既存データを維持しなければならない。
Proposalの承認はTaskの追加として扱い、既存Taskを暗黙に削除または置換してはならない。
削除、全消去、承認などの不可逆または広範な操作は、対象と結果を示した明示的な確認を
必要とする。

### IV. fx依存の隔離

vercel-labs/fx固有のAPI、データ型、認証、実行制御は専用アダプター内へ隔離し、
タスク管理コアから直接参照してはならない。fxの更新、障害、または将来の置換によって、
保存済みTaskやProposalの読み書きが不可能になってはならない。コアとfxアダプター間の
契約は明示し、モデルやプロバイダーに依存しない形で検証可能にする。

### V. 自動検証を品質ゲートとする

タスク操作、Proposalの検証・承認、親子関係などのドメイン規則はユニットテストで
検証しなければならない。fx連携はアダプター境界の契約テストを持ち、通常のテストは
実際のモデル応答に依存してはならない。保存処理は成功経路だけでなく、不正入力、
中断、書き込み失敗、既存データ破損を含む失敗経路も検証する。不具合修正には、修正前の
不具合を再現し、修正後に通過する回帰テストを追加しなければならない。ネットワークや
認証を必要とするテストは、決定的な通常テストスイートから分離する。

## セキュリティと運用上の制約

- fxによる外部モデルの利用は製品の前提とし、モデル呼び出しごとの説明や確認は要求しない。
- モデル呼び出しは、Proposal生成など利用者の明示的な操作を起点としなければならない。
  Issue選択、アプリ起動、データ更新だけを理由に自動開始してはならない。
- エージェントの調査範囲は利用者が選択したワークスペース内に限定しなければならない。
- 認証情報、秘密鍵、トークン、環境変数、Git認証情報をモデルへ送信してはならない。
- 送信対象と除外規則を設定可能にし、秘密情報をプロンプト、モデル応答、ログへ意図的に
  永続保存してはならない。
- モデル呼び出しの自動再試行には有限の上限を設けなければならない。
- 診断情報、トレース、プロンプト、モデル応答の外部送信は、通常のProposal生成とは
  別の明示的な利用者操作を必要とする。
- 初期開発はコマンドコアとCLIに集中し、TUI固有機能はコアの契約を安定させた後に扱う。
  将来のTUI要件を理由に、未使用の抽象化や重複実装を先行導入してはならない。

## 開発ワークフローと品質ゲート

1. すべての変更は、影響する原則、ユーザーストーリー、受け入れ条件を明示する。
2. 実装前に、コア、CLIアダプター、fxアダプター、永続化のどの境界へ属するかを決める。
3. 実装と同じ変更内で、必要なユニットテスト、契約テスト、回帰テストを追加または更新する。
4. レビュー前に通常テストスイートを通過させる。ネットワークや認証を必要とするテストは
   別ジョブとして実行し、未実行の場合はその理由を記録する。
5. データ形式、削除動作、Proposal承認動作を変更する場合は、移行方法、後方互換性、
   失敗時の復旧方法を文書化する。
6. 原則に反する複雑性や例外が必要な場合は、理由、影響範囲、解消条件を計画またはレビューに
   記録しなければならない。

## Governance

本constitutionは、プロジェクト内の他の開発慣行や個別の設計判断より優先する。
改正には、変更理由、影響を受ける原則または節、必要な移行措置を文書化し、レビューで
明示的な承認を得なければならない。すべての仕様、実装計画、コードレビューは本constitution
への準拠を確認し、違反や例外を未記録のまま受け入れてはならない。

バージョンはセマンティックバージョニングに従う。後方互換性のない原則の削除または再定義は
MAJOR、新しい原則や節の追加または実質的な拡張はMINOR、意味を変えない明確化や表記修正は
PATCHとする。改正時はSync Impact ReportとLast Amendedを更新する。定期的な適合確認に加え、
各機能仕様、実装計画、リリース候補のレビュー時に原則と品質ゲートへの準拠を確認する。
